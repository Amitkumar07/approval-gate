approval-gate

A drop-in approval gate and audit trail for AI agents. Before your agent sends an email, deletes a record, or calls an API it shouldn't call unsupervised, approval-gate pauses it, shows a human exactly what it's about to do, flags anything sensitive in the payload, and waits for approve / edit / reject — with a permanent record of what happened.

Why this exists

LangGraph already gives you interrupt() for human-in-the-loop control — that part is free and built in. What's missing is everything around it: a place to log what was proposed, a way to flag sensitive data before a human sees it (or before it sits in a log file), and a consistent pattern so every tool in a codebase pauses the same way instead of every team hand-rolling it slightly differently.

What this is not
Not a full observability platform, not an MCP vulnerability scanner, not an enterprise compliance suite. This sits alongside those tools, it doesn't replace them.

The five pieces

ApprovalGate

The object you call. Scans args, checks policy, waits on a backend, writes the audit record.

Backend

How the pause happens and how a decision comes back — browser, Slack, email, webhook, LangGraph, or a plain callback.

Policy

Optional. Skips the human step for low-risk actions, or routes high-risk ones to a specific reviewer.

PII scanner

Regex + optional Presidio. Masks emails, cards, secrets, and more before anything is shown or logged.

Audit log

SQLite, append-only. Every proposal, decision, and result — nothing is ever deleted.

Get started

Architecture

Two diagrams: what happens on every single call to request_approval(), and how that generalizes across the different ways a decision can come back.

The request lifecycle

Every call scans, logs a pending row, then optionally short-circuits via policy before ever reaching a human. This is the one flow that's identical no matter which backend or policy you're using.

How a decision comes back

backend.wait_for_decision() blocks the calling thread. What unblocks it is different per channel, but four of the six backends (everything except LangGraph and the plain-Python callback) share the same underlying shape: register a per-request queue, notify some external system, block on the queue, and let an HTTP handler running on a different thread deliver the result.

Get started

Quickstart

The fastest way to see the whole loop, no setup required.

# no LangGraph, no credentials, nothing to configure
git clone <repo>
cd approval-gate
pip install -r requirements.txt
python examples/plain_python_demo.py

For your own code, the shape is always the same:

from approval_gate import ApprovalGate

gate = ApprovalGate(db_path="audit.db")  # defaults to LangGraphBackend

def send_email(to, subject, body):
    decision = gate.request_approval(
        action_name="send_email",
        args={"to": to, "subject": subject, "body": body},
        risk="medium",
    )
    if not decision.approved:
        return f"BLOCKED: {decision.reason}"

    result = really_send_email(**decision.args)  # reflects any edits
    gate.log_result(decision.audit_id, result)
    return result
Not using LangGraph?
Pass backend= — see any page under Channels in the sidebar. Everything else about this snippet stays identical.

Install

pip install approval-gate
# only if you're using LangGraphBackend:
pip install "approval-gate[langgraph]"
# optional, richer PII detection:
pip install presidio-analyzer
python -m spacy download en_core_web_sm

The core package (ApprovalGate, the audit log, PII scanning, BlockingBackend) has no required dependencies. EmailBackend, SlackBackend, and WebhookBackend use only the Python standard library — nothing extra to install for those.

Channel · WebBackend

Browser

A real review inbox in a browser tab. The only channel where a reviewer can edit proposed arguments before approving, and the only one built for several pending items at once.

Best for
Active development, a team watching a dashboard, or whenever in-place editing of arguments matters. 
from approval_gate import ApprovalGate
from approval_gate.backends import WebBackend

backend = WebBackend(port=8642)
gate = ApprovalGate(db_path="audit.db", backend=backend)
print(f"Review inbox running at {backend.url}")
# ... call gate.request_approval(...) as usual, from any thread ...
backend.shutdown()

Open backend.url. Pending actions appear as rows in a tabular list — click one to expand it inline, edit any field, and Approve / Approve with edits / Reject. Every other pending item stays collapsed, same interaction model as a mail client.

Endpoints

GET /The inbox page itself
GET /api/pendingJSON list of everything currently waiting
POST /api/decide{audit_id, decision, by, reason, args} → resolves it

Try it: python examples/web_inbox_demo.py

Channel · WebhookBackend

Bring your own system

POSTs the pending action to a URL you configure; your system POSTs the decision back. For teams with their own ticket queue or admin panel who don't want to adopt Slack or email specifically for this. 

from approval_gate.backends import WebhookBackend

backend = WebhookBackend(
    notify_url="https://internal-tools.example.com/incoming",
    host="127.0.0.1", port=8643,
)
gate = ApprovalGate(db_path="audit.db", backend=backend)

Every pending action is POSTed as JSON with a callback_url field included. Your system decides however it wants, then calls that URL back: 

curl -X POST "$callback_url" -H "Content-Type: application/json" -d '{
  "audit_id": "...", "decision": "approve", "by": "your-system", "reason": ""
}'
Method & pathPurpose
GET /pendingPoll instead of relying on the initial POST
POST /decideYour system delivers the decision here

Try it: python examples/webhook_demo.py

Channel · EmailBackend

Email

Signed one-click approve/reject links. No login, no browser tab that has to stay open — the email just sits in an inbox until someone acts on it. 

from approval_gate.backends import EmailBackend

backend = EmailBackend(
    smtp_host="smtp.example.com", smtp_port=587,
    smtp_user="bot@example.com", smtp_password="...",
    from_addr="approval-gate@example.com", to_addr="reviewer@example.com",
    secret="a-random-string-you-generate-once",
    public_base_url="https://approvals.example.com",
)
gate = ApprovalGate(db_path="audit.db", backend=backend)

Clicking a link opens a confirmation page (so a mail scanner pre-fetching the link can't silently decide on the recipient's behalf); confirming resolves it. Links are HMAC-SHA256 signed so one can't be edited into approving a different action.

Does not prove the clicker is the recipient
The signature stops tampering, not link-sharing — anyone with the link (forwarded, leaked from mail logs) can use it. Use WebBackend or SlackBackend if that tradeoff isn't acceptable.

Two things to get right

  • secret — generate one random string once and keep it stable. Rotating it invalidates every link already sent.
  • public_base_url — must be reachable by the reviewer's browser, not localhost unless they're on the same machine.

args cannot be edited from an email link — only approve/reject.

Try it: python examples/email_demo.py (uses a local fake SMTP server, no real mail account needed)

Channel · SlackBackend

Slack

Interactive Approve/Reject buttons right in a Slack message, resolved without leaving Slack. Different (and more capable) than SlackNotifier, which only sends a link elsewhere — this backend receives the click back and resolves the decision itself.

One-time Slack app setup

  1. Bot token with chat:write scope; invite it to the target channel.
  2. Enable Interactivity; set the Request URL to wherever this listener is reachable from Slack's servers — a tunnel like ngrok in development, real ingress in production.
  3. Copy the bot token (xoxb-...) and the app's Signing Secret.
from approval_gate.backends import SlackBackend

backend = SlackBackend(
    bot_token="xoxb-...",
    signing_secret="...",
    channel="#approvals",
    host="0.0.0.0", port=8645,
)
gate = ApprovalGate(db_path="audit.db", backend=backend)

args aren't editable from Slack, same tradeoff as email.

Try it: python examples/slack_demo.py (fakes the outbound post; the inbound signed interaction is real)

Channel · LangGraphBackend default

LangGraph

The default backend — if you don't pass backend=, this is what you get. Use it if your agent is a LangGraph graph already driven by interrupt() / Command(resume=...). 

from langgraph.types import Command

result = graph.invoke(initial_state, config)
while "__interrupt__" in result:
    pending = result["__interrupt__"][0].value
    decision = ask_a_human_somehow(pending)
    result = graph.invoke(Command(resume=decision), config)

approval_gate.cli.run_with_cli_approval(graph, initial_state, config) wraps this loop with a terminal prompt if you just want something working immediately.

Resume-replay
When a node calling interrupt() is resumed, LangGraph re-runs that node function from the top — any code before the interrupt() call runs again. ApprovalGate handles this automatically via deterministic audit-row IDs and an upsert — see Audit log.

Try it: python examples/email_agent_demo.py

Channel · BlockingBackend

Plain Python callback

A script, a notebook, a raw tool-calling loop — anywhere with no framework and no need for anything async. 

from approval_gate.backends import BlockingBackend

def ask_a_human(pending):
    print(pending["action"], pending["args"])
    choice = input("approve/reject? ")
    return {"decision": "approve" if choice == "approve" else "reject", "by": "amit"}

gate = ApprovalGate(db_path="audit.db", backend=BlockingBackend(ask_a_human))

reviewer runs synchronously right there in the calling thread — no pause/resume plumbing, no server. This is also the simplest reference implementation to read if you're building a new Backend yourself.

Try it: python examples/plain_python_demo.py

Component

ApprovalGate

approval_gate/core.py — the object you call. Orchestrates everything else; owns no policy or channel logic of its own.

ApprovalGate(
    db_path: str = "audit.db",
    default_thread_id: str = "default",
    backend: Backend | None = None,   # defaults to LangGraphBackend
    policy: Policy | None = None,
)

request_approval

gate.request_approval(
    action_name: str,        # e.g. "send_email" -- shown to reviewers, matched by Rule
    args: dict,                # scanned for PII, editable by some backends
    risk: str = "high",      # "low" | "medium" | "high" -- your label
    thread_id: str | None = None,
) -> Decision

What it does, in order:

  1. Scans args for PII/secrets via pii.scan()
  2. Writes a pending row to the audit log (upsert_pending)
  3. If a policy is set, gives it first look — may short-circuit here
  4. Otherwise blocks on backend.wait_for_decision(pending)
  5. Writes the final decision (record_decision) regardless of which path was taken
  6. Returns a Decision

Decision

Decision(
    approved: bool,    # True for "approve" or "edit"
    args: dict,          # final args -- reflects edits if the reviewer changed anything
    reason: str,          # only set when rejected
    audit_id: str,          # pass to gate.log_result(...) after acting on it
)

After acting on an approved decision, call gate.log_result(decision.audit_id, result, error=False) — a separate step, because the result usually isn't known until after the action actually runs.

Component

Audit log

approval_gate/audit.py — a permanent, append-only SQLite record. Rows are never deleted, including rejected or errored actions.

Deterministic IDs

Rows are keyed by hash(thread_id, action_name, args), not an autoincrement or random UUID. This exists specifically for LangGraph: when a node calling interrupt() is resumed, LangGraph re-runs that node function from the top, so "create a pending audit row" runs again on every resume. A deterministic ID + UPSERT makes that replay harmless — it overwrites the same row instead of creating a duplicate.

A real bug this shape prevented recurring
Concurrent writes from multiple threads (an agent doing parallel tool calls) to one shared sqlite3.Connection without a lock don't just error — they can corrupt the database file on disk. Every public method on AuditLog takes a threading.RLock for its full duration. This was a real, found-in-development bug, not a hypothetical — see the git history around this file for the incident.

Multi-process safety

The connection is opened with PRAGMA journal_mode=WAL and a 5s busy_timeout, which is separate from the thread-safety lock above: it's what lets more than one OS process on the same machine write to the same db_path concurrently without one writer blocking every reader, or a brief lock conflict raising database is locked immediately instead of retrying.

Not a distributed database
WAL mode is a single-machine, single-filesystem mechanism. It covers "a couple of worker processes on one box," not a horizontally-scaled deployment across multiple machines — see SECURITY.md in the repo for the real ceiling.

Reading it back

from approval_gate import AuditLog

log = AuditLog("audit.db")
for record in log.list_all():
    print(record.action_name, record.status, record.decided_by)
fieldmeaning
statuspending / approved / rejected / edited / error
decided_byreviewer identity, or policy:<rule-name> for auto-decisions
final_argsonly set if the reviewer edited the proposed args
pii_findingsmasked, never the raw sensitive value

list_pending() returns only undecided rows — useful for a "what's stuck" check.

Component

PII / secret scanning

approval_gate/pii.py — every string-valued field in args is scanned before it's shown to a reviewer or written to the log.

Always on

Regex: emails, phone numbers, Luhn-validated card numbers, SSN-shaped numbers, and API-key-shaped strings (OpenAI, AWS, GitHub, Slack, Google patterns).

Optional

If presidio-analyzer is installed, adds NLP-based name/location/organization detection.

Card numbers are Luhn-checked, so a 16-digit order number like 1234 5678 9012 3456 is not flagged — only numbers that actually pass the checksum real card numbers use.

Masking

Findings are masked before they're shown or logged — pr***...om, never the raw value, even in your own audit database. pii.using_presidio() confirms which mode is active.

typeexample finding
emailpr***************om
card_number4242********4242
api_secretsk-***...***aaa
phone+9***********10
ssn_like12***-***89
Component

Policies

approval_gate/policy.py — pausing for a human on every call doesn't scale. Past a handful of action types, reviewers start rubber-stamping everything, which defeats the point. 

from approval_gate.policy import Rule, RulePolicy

policy = RulePolicy([
    Rule(risk="low", has_pii=False, auto_approve=True, name="auto-low-risk"),
    Rule(action_prefix="delete_", route_to="oncall-reviewer"),
    Rule(action_name="wire_transfer", auto_reject=True, name="block-wire-transfers"),
])
gate = ApprovalGate(db_path="audit.db", policy=policy)

Rules are evaluated in order, first match wins.

fieldmatches on
action_nameexact action name
action_prefixaction name starting with this string
riskthe risk= passed to request_approval
has_piiwhether any PII/secret findings were detected

What a matching rule does

effectbehavior
auto_approve Decided instantly. decided_by = policy:<rule-name>. Nothing shows up in any review channel, no notifier fires. Still fully logged.
auto_reject Same, but rejected — for actions that should never run unattended.
route_to Does not auto-decide. Still goes to a human; tags the pending payload so the backend/notifier can direct it.

Nothing matches, or no policy= at all → every action goes to a human. The safe default.

Policies must be pure
Like everything before a pause, a policy can re-run on a LangGraph resume-replay — no side effects.
Component

Notifiers

approval_gate/notifiers.py — a pending action sitting in a browser tab nobody has open doesn't help. notifier= on WebBackend fires the moment something's queued. 

from approval_gate.backends import WebBackend
from approval_gate.notifiers import SlackNotifier

backend = WebBackend(
    port=8642,
    notifier=SlackNotifier(webhook_url="https://hooks.slack.com/services/..."),
)
Notifier vs. SlackBackend
SlackNotifier posts to a Slack incoming webhook — one-way, it can only send a link elsewhere. SlackBackend is two-way and resolves the decision itself, inside Slack. Use a notifier for a ping into some other review surface; use SlackBackend when you want the decision to happen in Slack directly.

Write your own — it's just a function:

def my_notifier(pending: dict, review_url: str) -> None:
    my_paging_system.send(f"{pending['action']} needs review: {review_url}")

backend = WebBackend(port=8642, notifier=my_notifier)

A broken notifier (webhook down, bad credentials) is caught and logged, never allowed to block the approval flow — the pending action just sits there waiting, same as if there were no notifier at all.

Try it: python examples/notifier_demo.py

Troubleshooting

ModuleNotFoundError: No module named 'langgraph'

You're using the default backend without installing the extra. Either pip install "approval-gate[langgraph]", or pass a different backend= if you're not actually using LangGraph.

A Slack/email/webhook backend never resolves — request_approval just hangs

There is no timeout by design. Check:

  • Is the listener actually reachable from wherever the click/callback is coming from? (localhost isn't reachable from Slack's servers or a real mail client.)
  • For SlackBackend: does the Request URL in your Slack app config actually point at this process?
  • GET {backend.url}/pending (every async backend exposes this) shows what's currently stuck waiting.

"Invalid or tampered link" / "invalid Slack signature"

The secret / signing_secret used to verify doesn't match what signed the request. For email, this happens if secret changed since the email was sent — links don't survive a secret rotation. For Slack, confirm you copied the Signing Secret, not the bot token.

Two reviewers click at the same time / a link gets clicked twice

The second one gets a 404 (webhook/email) or a friendly "already decided" response (Slack) — whichever decision arrives first at the backend wins; the audit log records that one.

Duplicate rows in the audit log after a LangGraph resume

Shouldn't happen — rows are keyed by a deterministic hash specifically so a resume-replay upserts instead of duplicating. If you're seeing duplicates, check that thread_id is stable across the resume.

Concurrent request_approval() calls from multiple threads

Supported and tested — AuditLog locks around every access specifically to make this safe. If you're doing parallel tool calls from an agent, this is fine.

Deploying Email / Slack / Webhook somewhere real

These backends' HTTP listeners are stdlib http.server, which isn't hardened for internet-facing traffic on its own — put a real reverse proxy in front for TLS and basic abuse protection. See SECURITY.md in the repo for secrets handling and the full guidance.
